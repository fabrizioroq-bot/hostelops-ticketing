# Deployment Guide

This guide covers: local setup, configuring Supabase, deploying to
Vercel + Supabase (recommended) or Docker on a VPS (alternative), creating
the first admin user, and running the guest deduplication process.

## 1. Prerequisites

- Node.js 20+ and npm
- Python 3.11+ (3.13 recommended — see note below on 3.14+)
- A Supabase account (https://supabase.com) — free tier is enough to start
- (Optional) A Resend account for weekly PDF report emails
- (Optional) Mews Connector API credentials, if you want live PMS sync

> **Python version note:** at the time this project was built, `pydantic-core`
> did not yet have a compatible wheel for Python 3.14, and installing it
> falls back to a Rust build that can fail. Use Python 3.11–3.13 for the
> backend virtualenv.

## 2. Create the Supabase project

1. Create a new project at https://supabase.com/dashboard.
2. Go to **Project Settings → API** and copy: `Project URL`, `anon public`
   key, `service_role` key, and (under **JWT Settings**) the `JWT Secret`.
3. Go to **Authentication → Sessions** and set the **Access token (JWT)
   expiry** to `1800` seconds (30 minutes), matching the required session
   timeout. Combined with the frontend's inactivity auto-logout, this
   satisfies the "auto-timeout after 30 min inactivity" requirement.
4. Go to **Authentication → Providers** and confirm Email/Password is
   enabled (it is by default). Disable "Confirm email" for local dev if you
   want to log in immediately after creating seed users (production should
   keep it enabled).
5. Go to the **SQL Editor** and run the migrations in order, exactly as
   they appear in `supabase/migrations/`:
   1. `0001_init.sql` — schema, RLS policies, MDM tables
   2. `0002_auth_trigger.sql` — auto-creates `app_users` on signup
   3. `0003_seed.sql` — original demo seed (5 hostels, 10 users, 50 tickets)
   4. `0004_dashboard_functions.sql` — dashboard aggregation RPC functions
   5. `0005_new_enum_values.sql` — adds the `maintenance` role and related audit actions
   6. `0006_maintenance_module.sql` — maintenance tickets/photos tables, RLS, storage bucket
   7. `0007_scope_guest_tickets_from_maintenance_role.sql` — isolates the maintenance role from guest data
   8. `0008_replace_seed_data.sql` — replaces the demo roster/hostels with the real rb-horeca ones (keeps the demo admin, deletes/re-seeds everything else, adds sample maintenance tickets)

   (Alternatively, install the Supabase CLI and run `supabase db push` from
   the repo root, pointed at your project.)

   All 10 seeded users share the password `HostelDemo#2026` — **rotate or
   delete these accounts before going to production.**

## 3. Backend setup (FastAPI)

```bash
cd backend
python3 -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env
# edit .env with your Supabase URL/keys/JWT secret (see step 2)
```

Run the tests (no live Supabase project needed — they use an in-memory
fake of the Supabase query builder):

```bash
pytest -q
```

Run the API locally:

```bash
uvicorn app.main:app --reload --port 8000
```

Visit `http://localhost:8000/docs` for interactive API documentation
(Swagger UI, auto-generated by FastAPI).

## 5. Deploying to Vercel + Supabase (recommended path)

**Database/Auth** is already hosted by Supabase from step 2 — nothing more
to deploy there.

**Backend (FastAPI)** — Vercel doesn't natively run long-lived Python
processes well; deploy the backend to a container platform instead
(Railway, Render, Fly.io, or a small VPS all work identically since it's
a standard Dockerfile):

```bash
cd backend
docker build -t hostelops-backend .
# Push to your registry of choice, then deploy the image with these
# environment variables set (from backend/.env.example):
#   SUPABASE_URL, SUPABASE_ANON_KEY, SUPABASE_SERVICE_ROLE_KEY,
#   SUPABASE_JWT_SECRET, CORS_ORIGINS, MEWS_CLIENT_TOKEN, RESEND_API_KEY, ...
```

Set `CORS_ORIGINS` to your deployed frontend's URL (e.g.
`https://hostelops.vercel.app`).

**Frontend (Vercel)**:

```bash
cd frontend
vercel
```

In the Vercel project settings, add environment variables:
`VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`, `VITE_API_BASE_URL` (pointing
at your deployed backend). Redeploy after adding them (Vite bakes them in
at build time).

## 6. Alternative: Docker on a single VPS

```bash
cp backend/.env.example backend/.env   # fill in real values
docker compose build \
  --build-arg VITE_SUPABASE_URL=https://your-project.supabase.co \
  --build-arg VITE_SUPABASE_ANON_KEY=your-anon-key \
  --build-arg VITE_API_BASE_URL=https://your-domain.com/api
docker compose up -d
```

Put a reverse proxy (nginx, Caddy, or Traefik) in front of both containers
for TLS termination — the app must be served over HTTPS in production per
the security requirements.

## 7. Creating the first admin user

If you ran the seed migration, `admin@hostelops.example` already exists.
To create a fresh admin instead (e.g. for a real deployment where you
deleted the seed users):

1. Log in as any existing admin and use **Users → Add User** in the app, or
2. Call the API directly once you have *any* authenticated admin session:
   `POST /users` with `{"email": ..., "full_name": ..., "role": "admin",
   "hostel_ids": [], "temporary_password": "..."}`.
3. For the very first admin on a brand-new project (no admin exists yet),
   use the Supabase Dashboard: **Authentication → Users → Add User**,
   create the auth user, then in the SQL Editor run:
   ```sql
   update app_users set role = 'admin' where email = 'you@yourcompany.com';
   ```
   (The `app_users` row is created automatically by the `0002_auth_trigger`
   trigger the moment the auth user is created.)

## 8. Running the deduplication process

Guest merges are **manual-review-only** — nothing merges automatically.
As an admin or supervisor:

1. Go to **Deduplication Review** in the app and click **Scan for
   Duplicates** (or `POST /dedup/scan` directly). This compares all guest
   golden records using fuzzy name matching plus exact phone/reservation
   overlap, and inserts any newly-found pairs into the review queue.
2. Review each candidate's match score and reason, then **Approve Merge**
   (combines the two guest records, reassigning all of that guest's
   tickets to the surviving record) or **Reject** (the pair won't be
   suggested again).
3. Re-run the scan periodically (e.g. weekly) as new tickets and guests
   accumulate — it's cheap to run and only ever proposes candidates, never
   changes data on its own.

## 9. Weekly PDF reports

Configure `RESEND_API_KEY` and `RESEND_FROM_EMAIL` in the backend's `.env`.
The scheduler (started automatically with the FastAPI app) emails a PDF
summary to every active admin/supervisor every Monday at 07:00 server
time. To test it immediately without waiting for Monday, call
`GET /reports/weekly.pdf` (downloads the PDF directly) as an admin or
supervisor.

## 10. Maintenance module

A separate module from the guest ticketing system — its own table
(`maintenance_tickets`), its own role (`maintenance`), and its own Supabase
Storage bucket (`maintenance-photos`, created by migration `0006`) for
repair photos. Access:

- **admin**: full access, all hostels.
- **supervisor**: view-only, scoped to their assigned hostels.
- **maintenance role**: create/view/update, scoped to their assigned hostels.
- **agent**: no access at all.

No extra environment variables are needed — photo uploads go through the
backend (`POST /maintenance-tickets/{id}/photos`, multipart), which writes
to the bucket using the service-role key and returns short-lived signed
URLs for display, so the bucket itself stays private with no public/anon
access.

## 11. Backups

Supabase Pro and above includes daily automated backups with
point-in-time recovery configurable in **Project Settings → Backups**. On
the free tier, schedule your own periodic `pg_dump` (e.g. via a cron job
calling `supabase db dump`) if you need backups before upgrading.
